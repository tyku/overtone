# План развития пайплайна Overtone

Реализованы frontend и блок сохранения/API: PostgreSQL, история, запись/завершение, multipart, S3, идемпотентность, force-close и долговечное намерение обработки. Следующий отдельный блок — worker/очередь, RunFullPipeline и получение результатов. Инструкции и фактические ограничения: README.md. Ниже сохранён исходный план обсуждения.

Дата: 2026-09-05. Статус: план для совместного проектирования; решения ниже — предложения, а не утверждённая спецификация.

Ход проектирования: согласованный пользовательский сценарий записан в [FRONTEND_FLOW.md](FRONTEND_FLOW.md) и имеет приоритет над предложениями этого плана. Пункт 1 в работе: сценарий приёма определён, ID приёма генерирует backend; единое название — `requestId` в Overtone и `request_id` в gRPC medical-scribe. Один приём содержит одну логическую аудиозапись; отдельный `recordingId` убирается, часть определяется через `requestId + partNo`. Пользователь получает один итоговый документ; выбран единый `RunFullPipeline` с SLO 30 секунд от подтверждённого сохранения до готового отчёта. Это не таймаут. Параметры обработки пока зашиты на стороне сервиса, пользователь их не выбирает; пользователю выдаётся `clinical_document.md`. Пока показываем Markdown как форматированный текст и даём скачать `.md`; решение временное, в будущем вероятен JSON. Ранее предложенная возможность отдельной повторной обработки с изменением настроек пользователем не утверждена; пдавайерезапись аудио исключена.

## Цель и границы

Согласованная граница частей: номера частей нужны только для загрузки, повторов и склейки на backend. После склейки вход обработки — единое аудио в S3, связанное с `requestId`. Отдельный `partId` не вводится; части не являются сущностями дальнейшего вычислительного пайплайна.

Согласованный пользовательский результат: один итоговый документ после обработки аудио, разбора диалога, определения ролей и формирования отчёта. Выбран единый вызов `RunFullPipeline`; SLO — 30 секунд от подтверждённого сохранения (S3 и закрытие в БД) до доступного отчёта, включая ожидание очереди, вычисления и получение результата. Это не таймаут: превышение само по себе не отменяет задачу и не запускает retry. Достижение SLO пока не проверено, пользователю выдаётся `clinical_document.md`. Пока показываем Markdown как форматированный текст и даём скачать `.md`; решение временное, в будущем вероятен JSON. Внутренние вычислительные этапы остаются в medical-scribe.

Overtone принимает один или несколько аудиофайлов по HTTP, собирает единое аудио, сохраняет его в S3, организует асинхронную обработку через medical-scribe, получает и сохраняет результат для клиента. Overtone владеет состоянием, расписанием, повторами, отменой и восстановлением задач. API, фоновые обработчики и frontend пока могут оставаться в одном проекте.

medical-scribe выполняет вычислительные команды и читает/пишет S3. Очередь и бизнес-состояние в него не переносятся. Сервис уже содержит GPU- и LLM-этапы; внутренние вычислительные алгоритмы остаются там.

Гарантия: подтверждённая задача не теряется при поддерживаемых сбоях, восстанавливается и доходит до успеха, отмены или зафиксированной ошибки после исчерпания политики повторов. Гарантировать успешную обработку любого файла невозможно. Повторное исполнение допустимо, повторное принятие результата одной попытки — нет. Модель отказов, сохранность БД/S3 и границу ответственности до подтверждения загрузки нужно определить явно.

## Что есть сейчас

| Область | Фактическое состояние |
|---|---|
| HTTP | `backend/src/recordings.controller.ts`: один бинарный сегмент на `POST /api/recordings`; последний обозначается `X-Recording-Complete`. |
| Приём | `recording-storage.service.ts`: временные файлы, локальное сохранение сегментов, проверка наличия сегментов 1..N. |
| Сборка | `recording-audio-encoder.service.ts`: FFmpeg concat → M4A/AAC 64 kbit/s; выполняется внутри последнего HTTP-запроса. |
| S3 | `recording-transfer.service.ts`: загрузка в `requests/{sessionId}/input/{recordingId}.m4a`, затем удаление локального M4A. Абстракция ObjectStorage поддерживает только upload. |
| Идемпотентность | Наличие локального файла и Map активных операций внутри процесса; долговечной записи о завершённой загрузке нет. |
| Frontend | IndexedDB, последовательная отправка сегментов, удаление локальной записи после ответа с `finalFileName`; состояния обработки и результата нет. |
| БД/очередь | Есть Compose для MongoDB и Redis; в backend нет подключения БД, очереди, gRPC-клиента или фонового восстановления. |
| Inference | `../medical-scribe/proto/inference.proto`: speech-core, speaker-roles, normalization, fact-extraction, composition; также clinical-path и full-pipeline. |
| Результат inference | Артефакты в S3, последним записывается `stage-result.json` с именами, ключами и SHA-256. Успех повторной команды определяется по этому манифесту. |

Замеченные ограничения, которые влияют на план:

- Повтор загрузки после успешного S3 и потери HTTP-ответа может заново собрать и перезаписать аудио; после удаления файлов нет долговечного подтверждения прежнего успеха. Другие байты под тем же номером существующего сегмента не сравниваются по checksum.
- Map не защищает от конкуренции между процессами и не восстанавливает работу после рестарта.
- Документ `medical-scribe/docs/GPU_API_CONTRACT.md` описывает только два этапа и обещает поведение timeout, которого обработчики сейчас не реализуют: `timeout_seconds` из proto не передаётся исполнителю.
- Cancel/GetCommandStatus отсутствуют. Дубликат активной команды узнаётся только внутри одного процесса.
- `_run_command` запускает работу через `asyncio.to_thread` и освобождает reservation в `finally`. Нужно проверить и исправить сценарий отмены RPC, когда вычисляющий поток ещё работает, а reservation уже освобождён.
- В просмотренных server/handlers/executors нет общего ограничения на одновременное выполнение разных GPU-команд, хотя документация обещает одну speech-core команду.
- `RunFullPipeline` публикует документ и сведения о запуске, без промежуточных контрольных точек в S3. Выбор этого RPC определяет стоимость повторов.
- Версия клинического пайплайна есть в Python, но не передаётся текущим gRPC-контрактом.
- Redis Compose использует `allkeys-lru`. При выборе Redis как очереди конфигурацию сохранности и удаления ключей необходимо пересмотреть.

## Порядок совместного проектирования

### 1. Домен, границы операции и результат

- Развести приём/сессию, запись, загружаемые файлы, запуск обработки, этап и попытку команды.
- Определить соответствие `sessionId`, `recordingId`, `requestId`, `jobId`, `commandId`; несколько записей одного приёма не должны смешиваться.
- Определить: что означают несколько файлов, кто задаёт порядок, можно ли смешивать форматы, можно ли добавлять файлы после завершения загрузки.
- Согласовано: результат первой версии для пользователя — один файл `clinical_document.md`, полученный из S3 по манифесту `stage-result.json` полного запуска. Пока показываем Markdown как форматированный текст и даём скачать `.md`; решение временное, в будущем вероятен JSON.
- Согласовано: вызывать `RunFullPipeline` целиком и далее оптимизировать по замерам. SLO — 30 секунд от подтверждённого сохранения до доступного отчёта; это не технический таймаут. Отдельные вычислительные RPC в текущий план реализации не входят; сборка, сохранение входа, полный inference и получение результата остаются отдельными действиями Overtone.
- Согласовано: версия пайплайна, модели и LLM backend пока фиксированы на стороне сервиса, пользователь их не выбирает. При проектировании интеграции определить конкретные значения и способ фиксации конфигурации на запуск, чтобы повтор доставки не менял настройки команды.

Результат проектирования: сценарии пользователя, словарь идентификаторов, выбранная цепочка и состав результата.

### 2. Надёжный приём и завершение загрузки

- Согласовано: принимаем только аудио встроенного браузерного рекордера; загрузка пользователем готовых файлов пока не предусмотрена. MIME/кодеки и совместимость частей определить исходя из целевых браузеров.
- Согласовано: «Завершить приём» отправляет все части и их порядок одним `multipart/form-data` запросом; этот же запрос запускает склейку, сохранение S3 и закрытие в БД. При обрыве повторяется весь запрос. Отдельного HTTP-запроса закрытия нет. Уточнить структуру метаданных частей: количество, порядок, MIME, размер, checksum.
- Согласовано: принимать части во временные файлы на локальном диске backend и там склеивать единое аудио. Удалять временные части и собранный файл после S3 и фиксации закрытия в БД. Уборку неудачных загрузок, размещение файлов/worker и поведение при потере локального диска определить отдельно.
- Согласовано: идемпотентность завершения по `requestId`, без отдельного `uploadId`, с проверкой неизменности состава, порядка и содержимого аудио. Повтор тех же данных продолжает незавершённое сохранение или возвращает прежний успех; конфликт содержимого отклоняется. Механизм проверки ещё предстоит определить.
- Согласовано: закрытие приёма требует сохранения собранного аудио в S3 и смены статуса в БД. Только после подтверждения обоих действий клиент переходит на экран отчёта. При сбое успешное закрытие не состоялось. Однако состав аудио окончательно фиксируется по нажатию «Завершить приём»: дозапись после этого запрещена даже при ошибке; доступны retry того же аудио и принудительное закрытие. Прежняя договорённость о дозаписи после ошибки отменена. Способ ожидания и выполнение сборки внутри HTTP или фоновым обработчиком предстоит спроектировать с сохранением этой границы подтверждения.
- После подтверждённого сохранения аудио в S3 браузерную копию можно удалить. Если закрытие в БД ещё не завершилось, retry должен использовать сохранённое аудио S3 без повторного upload. При принудительном закрытии без подтверждения S3 браузер хранит аудио 2–3 часа; для реализации берём 3 часа от принудительного закрытия. Запрет дозаписи должен переживать перезагрузку страницы. Механизм атомарности бизнес-операции между S3 и БД и фиксацию намерения обработки предстоит спроектировать.
- Согласовано: продуктового ограничения длительности нет, часовые записи допустимы. Определить технические ограничения размера multipart-запроса, числа файлов, форматов и таймауты с учётом длительных записей; предусмотреть уборку незавершённых загрузок. Достижение SLO 30 секунд на длинных записях проверить измерениями.

Результат: HTTP-контракт, точка принятия ответственности сервером, правила восстановления и совместимости с текущим клиентом.

### 3. БД и состояние пайплайна

- Согласовано: у пользователя не более одного незакрытого приёма; создание нового до обычного или принудительного закрытия прежнего запрещено. После S3 и закрытия в БД следующий приём разрешён, даже если предыдущий отчёт ещё готовится. Пока владелец всех приёмов — один технический пользователь на backend, авторизация и управление пользователями отложены. Предусмотреть защиту от конкурентного создания.
- Спроектировать записи загрузок/сегментов, задач, этапов, попыток и артефактов, историю ошибок и переходов.
- Разделить статус, текущий этап и состояние отмены. Черновые статусы задачи: queued, running, retry_wait, succeeded, failed, cancelled; у загрузки собственный жизненный цикл.
- Согласовано представление для frontend: единый пользовательский статус, «Отчёт в обработке» включает ожидание и выполнение обработки, «Завершён» означает доступность итогового документа. Внутренняя фиксация закрытия остаётся отдельной: новый приём разрешён уже во время подготовки предыдущего отчёта. Публичные enum и состояния ошибок ещё обсуждаются.
- Согласован итоговый статус «Ошибка обработки» после окончательного сбоя и исчерпания retry. Пока автоматические повторы продолжаются, frontend показывает «Отчёт в обработке». Ошибка обработки не открывает приём заново и не блокирует создание следующего.
- Определить допустимые переходы, уникальные ограничения и атомарные условия обновления; поздний ответ старой попытки не меняет актуальный результат.
- Хранить неизменяемые входные ссылки/checksum, параметры запуска, resultKey, номер попытки, nextAttemptAt, сведения о владельце работы и сроке его полномочий.
- Согласовано: PostgreSQL. Облачного провайдера выбрать позднее; существующий MongoDB Compose не определяет целевую архитектуру. Сохранение/API и фоновое выполнение согласуются двумя отдельными блоками.

Результат: схема данных, индексы, таблица переходов и условия атомарной фиксации каждого перехода.

### 4. Очередь, worker и восстановление

- Выбрать очередь: долговечный список готовых задач в БД либо внешний брокер. При внешнем брокере спроектировать outbox — запись намерения отправить работу вместе с изменением состояния БД.
- БД остаётся источником истины; потеря сообщения не должна означать потерю задачи. Предусмотреть повторную публикацию и периодическую сверку.
- Разделить фоновые этапы: сборка → сохранение единого аудио в S3 → inference → получение/проверка результата → фиксация завершения.
- Забирать работу атомарно на ограниченное время, продлевать владение heartbeat-ом и восстанавливать просроченные задачи. Обновления от старого владельца отвергать по версии владения.
- Отдельно решить судьбу уже запущенной удалённой GPU-команды при утрате владения: запрет записи в БД не останавливает вычисления и не защищает S3 от конкурирующей публикации.
- Ограничить параллелизм FFmpeg, GPU и получения результатов; предусмотреть backpressure и корректное завершение процесса.

Результат: схема выполнения и восстановления, выбор механизмов очереди, правила конкурентного доступа.

### 5. Контракт выполнения medical-scribe

- Согласовать proto, код и документацию; определить поддерживаемые команды/версии и детерминированный mock для выбранной цепочки.
- Закрепить неизменность команды по `commandId`; при необходимости добавить fingerprint входа/параметров и отклонение конфликтов.
- Разделить повтор доставки неизвестно завершившейся команды с прежним ID и новую попытку после подтверждённой ошибки с новым ID. `IN_PROGRESS` не расходует бюджет вычислительных повторов.
- После потери ответа проверять манифест и состояние прежней команды. Отсутствие манифеста само по себе не доказывает, что команда больше не выполняется.
- Определить необходимость отдельного получения статуса, affinity к исполнителю и поведение при нескольких экземплярах inference.
- Реализовать реальные сроки исполнения и удержание reservation до фактического завершения работы; определить ограничение GPU-параллелизма.
- Описать отмену: Overtone запрещает следующие этапы и публикацию позднего результата; остановку активной команды реализует исполнитель в безопасной точке. Немедленную остановку неделимого вызова модели не обещать.

Результат: согласованный gRPC-контракт и небольшой перечень обязательных изменений medical-scribe без переноса туда очереди.

### 6. Повторы, отмена и гонки

- Разделить временную недоступность S3/сети/исполнителя, необрабатываемый вход и неопределённый исход RPC.
- Установить повторы по этапам: задержка с увеличением и случайным разбросом, лимит попыток и общий срок задачи. После исчерпания — видимая ошибка и ручной повтор.
- Если GPU уже закончил, а Overtone не прочитал S3 или не записал БД, повторять получение/фиксацию результата, сохраняя успешное вычисление.
- Определить отмену до запуска, между этапами, при активной команде и во время получения результата; задать атомарного победителя гонки отмены с завершением.
- Отделить пользовательскую отмену от подтверждения фактической остановки вычислений. Отмена не означает удаление исходного аудио.
- Согласовано принудительное закрытие приёма без успешного сохранения после неудачных retry: пользователь выходит из незавершённого сценария, приём и ошибки сохраняются для разбора, обработка не запускается. Браузерное аудио без подтверждённой копии S3 сохраняется на 2–3 часа (для реализации — 3 часа от принудительного закрытия), при подтверждении S3 его можно удалить раньше. Спроектировать отдельный терминальный исход и защиту от позднего завершения загрузки; хранение серверных файлов, сценарий восстановления и поведение при недоступной БД ещё открыты.

Результат: матрица ошибок и повторов, семантика cancel/retry, сценарии гонок.

### 7. Получение, хранение и выдача результата

- Расширить ObjectStorage операциями чтения, проверки наличия/метаданных и очистки.
- Прочитать stage-result.json, проверить версию, ожидаемый префикс задачи/команды, обязательные артефакты, размер и SHA-256 получаемых файлов.
- Хранить аудио и артефакты в S3; метаданные, связи и ссылки — в БД. Решить, нужно ли дополнительно сохранять разобранный документ в БД для редактирования/поиска.
- Фиксировать succeeded только после проверки необходимого результата и долговечной записи его доступности в БД.

### 8. Проверка гарантий и ввод в работу

- Сквозной сценарий с одним файлом и несколькими сегментами через mock, затем smoke на GPU.
- Сбой API после записи S3 до записи БД; сбой после записи БД до постановки в очередь; потеря HTTP-ответа после завершения загрузки.
- Рестарт worker на каждом этапе; два worker претендуют на одну задачу; просроченное владение и поздний ответ.
- Потеря gRPC-ответа после успешной обработки; повтор активной команды; рестарт inference; отмена RPC при продолжающемся потоке.
- Временная недоступность S3/БД/очереди, неполный манифест, неверная checksum, испорченное аудио, исчерпание повторов.
- Отмена одновременно с успехом, повтор HTTP complete/cancel/retry, конфликт содержимого загружаемого сегмента.
- Метрики возраста очереди, зависших задач, повторов, длительности этапов и ошибок; сквозные идентификаторы в логах без аудио/транскриптов.
- Обновить Compose, конфигурацию и runbook. Существующее аудио в S3 не ставить автоматически в обработку без явного решения о миграции.

Результат: исполняемая матрица отказов и критерии готовности.
