## Минимальный набор ручек

Согласовано: пока все ручки работают с одним техническим пользователем, которого определяет backend. Авторизация и управление пользователями реализуются позже. Правило одного незакрытого приёма применяется к этому пользователю; отдельный пользователь на вкладку или браузер не создаётся.

| Метод и путь | Назначение |
|---|---|
| `POST /api/requests` | Создать приём, вернуть серверный `requestId` и статус `created`. Новый приём нельзя создать, пока у пользователя есть незакрытый. |
| `GET /api/requests` | Список всех приёмов: дата/время создания, статус, открытие приёма; новые сверху, с пагинацией. Включает незавершённые, обработанные и принудительно закрытые приёмы. |
| `GET /api/requests/{requestId}` | Получить состояние приёма, сохранность аудио в S3, состояние обработки, готовность отчёта и ошибку; используется при восстановлении страницы и polling. |
| `POST /api/requests/{requestId}/complete` | Первично принять все части multipart-запросом, склеить, сохранить S3 и зафиксировать закрытие. Повтор продолжает незавершённые действия или возвращает прежний успех. |
| `POST /api/requests/{requestId}/abandon` | Явно закрыть без обработки; сохранить историю и разрешить начать следующий приём. |
| `GET /api/requests/{requestId}/report` | Выдать содержимое готового документа и сведения о формате. Сейчас Markdown; контракт должен допускать JSON в будущем. |

Согласованный конфликт создания: если у пользователя уже есть незакрытый приём, `POST /api/requests` возвращает HTTP `409`, код `ACTIVE_REQUEST_EXISTS` и `requestId` существующего приёма. Frontend предлагает вернуться к нему. Новый приём не создаётся, в том числе при конкурирующих запросах.

Согласовано: страница списка приёмов и открытие прошлых отчётов нужны сразу. Показываем дату и время создания, статус и кнопку открытия; новые приёмы сверху, с пагинацией. Список включает незавершённые, обработанные и принудительно закрытые приёмы. Техническую форму пагинации и поведение открытия незавершённых приёмов ещё предстоит определить.

## Согласованное требование к ошибкам завершения

`/complete` возвращает различимые машинные ошибки, чтобы frontend понимал, нужен ли retry с аудиофайлами или без них. По тексту сообщения или одному HTTP-коду клиент это не угадывает.

Согласованные коды ошибок и действия клиента. Дополнительное поле `retryAction` пока предлагается; его наличие и точную форму JSON-ответа ещё предстоит определить.

| Код | Когда возвращается | Действие клиента |
|---|---|---|
| `AUDIO_UPLOAD_REQUIRED` | Сервер достоверно установил, что пригодного сохранённого входа нет и нужны файлы клиента. | `retryAction: upload_audio` — повтор multipart с тем же аудио. |
| `REQUEST_FINALIZATION_FAILED` | Аудио в S3 подтверждено и идентифицировано, но закрытие в БД не завершилось. | `retryAction: complete_without_audio` — повтор без файлов. |
| `REQUEST_STATE_UNKNOWN` | Сервер не может надёжно определить, завершилось ли сохранение/закрытие. | `retryAction: check_status` — сверить состояние через GET, при недоступности повторить проверку позднее. |

При потере HTTP-ответа или сетевом timeout кода ошибки вообще может не быть: клиент также сверяет состояние. Нельзя трактовать недоступность S3/БД как доказанное отсутствие сохранённого аудио. Ошибки валидации и конфликты неизменности не должны предписывать автоматический retry; их коды и HTTP-статусы обсуждаются отдельно.

Возможность использовать готовый локальный файл на backend вместо повторного upload остаётся частью проектирования восстановления: `AUDIO_UPLOAD_REQUIRED` означает именно необходимость файлов клиента, а не просто отсутствие файла в S3.

## Что обсудить по каждой ручке

Согласованное представление состояния для frontend: один пользовательский статус. После успешного закрытия и в период ожидания/выполнения обработки — «Отчёт в обработке»; когда итоговый документ получен и доступен пользователю — «Завершён». Окончательный сбой обработки после исчерпания retry — «Ошибка обработки»; автоматические повторы до этого остаются в статусе «Отчёт в обработке». Ранее предложенное разделение публичных `status` и `processingStatus` этим решением заменяется. Конкретные значения enum и состояния ошибок сохранения ещё обсуждаются.

Внутренняя фиксация закрытия и готовность отчёта остаются разными событиями: следующий приём можно создать уже при статусе «Отчёт в обработке». Необходимые внутренние поля и `audioStored` проектируются отдельно; единственный публичный статус не должен менять согласованную атомарность закрытия или правила retry.

Согласованы остальные пользовательские статусы:

- «Создан» — запись можно вести до нажатия завершения.
- «Сохранение аудио» — завершение начато, дозапись запрещена.
- «Ошибка сохранения» — доступны retry и принудительное закрытие; дозапись запрещена.
- «Закрыт без сохранения» — принудительное закрытие.

Итого согласованы семь пользовательских статусов, включая «Отчёт в обработке», «Завершён» и «Ошибка обработки». Точные машинные значения и переходы фиксируются в едином техническом черновике. Клиентская фиксация аудио по нажатию завершения сохраняется даже при потере связи, когда серверный статус ещё не обновился.

Согласованный инвариант: один незакрытый приём на пользователя. Проверка должна выдерживать конкурентные запросы создания. После успешного сохранения S3 и закрытия в БД разрешено создать следующий приём, даже если отчёт ещё готовится; готовность отчёта не является дополнительной блокировкой. Обычный пользовательский сценарий — последовательные приёмы пациентов. До авторизации используется единый технический пользователь. Ответ при наличии незакрытого приёма согласован: `409 ACTIVE_REQUEST_EXISTS` и его `requestId`. Конкретное ограничение БД ещё предстоит определить.

1. Создание: тело запроса, идемпотентность при потере ответа/повторном клике, поля ответа.
2. Состояние: единый пользовательский статус, подтверждение `audioStored`, допустимые действия и ошибки. Определить enum статусов и отдельные внутренние признаки закрытия/обработки. Отсутствие данных/ошибка чтения S3 не должны выглядеть как достоверное `audioStored: false`.
3. Завершение: поля multipart и проверка неизменности аудио; сохранение последнего чанка до отправки; конкурирующие повторы; ответы до/после фиксации БД. Успешный ответ означает S3 + БД, без ожидания вычислений.
4. Повтор завершения после подтверждения S3: тот же `/complete` допускает вызов без аудиофайлов. Предлагается JSON-запрос на продолжение закрытия; сервер сам проверяет сохранённый вход. Если вход не подтверждён, возвращает понятную ошибку и требует аудио. Это повтор той же операции, а не обязательный второй запрос после каждого multipart.
5. Принудительное закрытие: идемпотентность, разрешённые состояния, гонка с `/complete`. Уже успешно закрытый приём не переводится в abandoned этим действием; отмена запущенной обработки проектируется отдельно.
6. Отчёт: форма ответа, поведение до готовности и при ошибке. Предложение — формат/версия и содержимое; `.md` frontend может скачать из уже полученного содержимого без отдельной ручки скачивания.
7. Общие вопросы: коды HTTP, единый формат ошибок, сетевые повторы. Сейчас приёмы принадлежат одному техническому пользователю; авторизация и админские ручки отложены по согласованию с пользователем.

Публичный запуск/повтор/отмена вычислений не добавляются автоматически к этому набору. Обычное успешное завершение приёма регистрирует обработку; retry оркестратора выполняется сервером. Пользовательские действия над уже запущенной обработкой относятся к дальнейшему обсуждению.

## Границы реализации

Выбор PostgreSQL не делает S3 и БД участниками одной транзакции. Требуется протокол сохранения входа, фиксации закрытия/намерения обработки и восстановления частичных сбоев. Контракт должен возвращать достаточно информации для безопасного удаления браузерной копии после подтверждения S3, даже если закрытие ещё требуется повторить.

Черновик не утверждает схему таблиц, очередь, S3 layout, JSON-формы ответов или технические таймауты. Их выбираем последовательно с пользователем.

## Блок 2: сохранение и API — согласованный вариант

### Протокол сохранения

1. По «Завершить приём» frontend сохраняет локальную фиксацию записи, принимает последний чанк и отправляет неизменяемый набор частей. Манифест содержит номер, имя multipart-поля, MIME, размер и SHA-256 каждой части в порядке склейки.
2. Backend принимает файлы на диск, проверяет комплектность, фактические размеры и checksum. Перед склейкой фиксирует в PostgreSQL манифест/его fingerprint и состояние `saving`. Последующие загрузки по этому `requestId` обязаны совпадать с зафиксированным входом.
3. Один владелец операции выполняет склейку и сохраняет единое аудио в S3. Сведения, позволяющие найти и проверить ожидаемый объект, фиксируются до внешней записи; для восстановления используется проверяемое подтверждение S3. Конкурирующие повторы не запускают вторую склейку/публикацию. Долгая транзакция БД на время HTTP, FFmpeg и S3 не удерживается.
4. После подтверждения S3 транзакция PostgreSQL фиксирует ссылку на аудио, закрытие приёма, публичный статус `processing` и долговечное намерение обработки. Именно эта фиксация разрешает следующий приём и подтверждение успеха клиенту. Механизм исполнения намерения разбирается в следующем блоке.
5. Если S3 записан, а транзакция БД не завершилась, возвращаем `REQUEST_FINALIZATION_FAILED` и разрешаем retry без файлов. Если исход записи БД неизвестен, используем `REQUEST_STATE_UNKNOWN`; по восстановлении связи проверяем фактическое состояние.
6. Потеря ответа не меняет исход: повтор проверяет PostgreSQL и при необходимости S3, продолжает незавершённые действия или возвращает прежний успех. Существующий успешно принятый вход не перезаписывается. Ошибка удаления временных файлов после закрытия не превращает успех в ошибку.

Для атомарности создания — ограничение БД «один незакрытый приём на пользователя». Для закрытия/abandon — атомарные условные переходы: победившее терминальное действие не может быть отменено поздним ответом другой операции. Конкретную схему владения и восстановления просроченных операций определить совместно с блоком фонового выполнения.

### Машинные статусы

`created`, `saving`, `save_failed`, `processing`, `completed`, `processing_failed`, `abandoned`.

Первые три блокируют создание нового приёма. Остальные разрешают. Локальный запрет дозаписи, установленный до отправки, не снимается из-за старого серверного `created`.

### Формы запросов и ответов

| Ручка | Предлагаемый контракт |
|---|---|
| `POST /api/requests` | Без доменных параметров; `201` с `requestId`, `status: created`, `createdAt`. Существующий незакрытый приём: согласованный `409 ACTIVE_REQUEST_EXISTS` с его ID. |
| `GET /api/requests` | Cursor-пагинация, `limit` по умолчанию 20, максимум 100; сортировка `createdAt DESC`, затем ID для устойчивого порядка. Ответ `items`, `nextCursor`. Элемент: `requestId`, `createdAt`, `status`. |
| `GET /api/requests/{id}` | `200`: `requestId`, `status`, `createdAt`, `updatedAt`, `audioStored: true/false/null`, `error: null` или объект ошибки. `null` означает неизвестную сохранность аудио, а не отсутствие. Неизвестный приём: `404 REQUEST_NOT_FOUND`. |
| `POST /api/requests/{id}/complete` | Первая отправка и необходимый повтор: multipart с JSON-полем `manifest` и полями файлов. Retry без аудио: JSON `{}` на ту же ручку. Успех: `200` с текущим состоянием приёма; S3 и закрытие в БД подтверждены, вычислений не ждём. Если операция ещё идёт: `202` с состоянием; это не подтверждение успешного закрытия, frontend продолжает ожидать. |
| `POST /api/requests/{id}/abandon` | JSON с необязательной причиной. `200` со статусом `abandoned`; повтор возвращает тот же результат. Закрытый обычным способом приём: `409 REQUEST_ALREADY_CLOSED`. При конкуренции итог определяет атомарный переход. |
| `GET /api/requests/{id}/report` | При готовности `200`: `requestId`, `format: markdown`, `schemaVersion: 1`, `content`. Пока отчёт не готов: `409 REPORT_NOT_READY`. Окончательная ошибка обработки: `409 REPORT_FAILED`. Неизвестный приём: `404 REQUEST_NOT_FOUND`. До готовности frontend использует status polling. |

Фронт скачивает `.md` из полученного `content`. В будущем формат JSON получит соответствующие `format`/`schemaVersion`; жизненный цикл приёма от этого не зависит.

### Ошибки и повтор

Форма ошибки: `error: { code, message, retryAction }` и `requestId`, если он известен. `retryAction` предлагает явное действие; HTTP-статус сам по себе не определяет повтор. Конкретные коды ошибок завершения уже согласованы, поля ответа и HTTP-сопоставление ниже — предложение.

- `409 AUDIO_UPLOAD_REQUIRED`, `retryAction: upload_audio`: нужны исходные файлы клиента; готовый локальный/S3 вход восстановить нельзя.
- `503 REQUEST_FINALIZATION_FAILED`, `retryAction: complete_without_audio`: вход S3 подтверждён, закрытие требует повтора.
- `503 REQUEST_STATE_UNKNOWN`, `retryAction: check_status`: исход неизвестен; не удалять локальное аудио без отдельного подтверждения S3.
- `409 AUDIO_CONTENT_CONFLICT`, `retryAction: none`: состав или содержимое отличаются от зафиксированного входа.
- Ошибки формата/пустого аудио: `400`/`422`, `retryAction: none`; фактическое превышение технического лимита запроса: `413`. Точные лимиты ещё не утверждены; продуктового лимита длительности нет.

Сбой связи без ответа обрабатывается как неизвестный исход: GET состояния с повтором при недоступности. Пока сервер достоверно продолжает операцию, frontend ожидает, а не создаёт параллельные загрузки.
