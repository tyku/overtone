# Client Contract: запись и отправка аудио

Этот документ фиксирует контракт клиентского приложения для MVP Overtone.

## Общая схема

Клиент — браузерное приложение/PWA для компьютера, телефона и планшета. Аудио не передаётся на сервер во время записи.

1. Пользователь начинает запись.
2. `MediaRecorder` формирует `WebM/Opus`-чанки примерно раз в секунду.
3. Каждый чанк сразу сохраняется локально в IndexedDB.
4. После остановки записи клиент отправляет аудио на сервер по HTTP.
5. Локальные данные удаляются только после подтверждения успешной загрузки сервером.

WebSocket для передачи аудио в MVP не используется.

## Локальное хранение

Основное хранилище MVP — IndexedDB. Аудио нельзя держать только в оперативной памяти вкладки.

Рекомендуемая модель данных:

```text
session
- id
- created_at

recording
- id
- session_id
- status: recording | ready | uploading | uploaded | failed
- mime_type
- started_at
- stopped_at
- expires_at

segment
- id
- recording_id
- segment_no
- started_at
- stopped_at

chunk
- segment_id
- chunk_no
- blob
- created_at
```

Запись логически связана с `session_id`. Одна запись может состоять из нескольких сегментов, например после перезагрузки страницы.

OPFS можно рассмотреть позднее для очень больших файлов или последовательной записи в файл. Для записей длительностью 15–20 минут в `WebM/Opus` IndexedDB достаточно.

## Размер и квота

Ожидаемый размер одной записи длительностью 15–20 минут — примерно 5–15 MB в зависимости от битрейта и содержимого. Если локально останутся 25 записей, это ориентировочно 125–375 MB.

Клиент должен:

- проверять доступное место через `navigator.storage.estimate()`;
- запрашивать persistent storage через `navigator.storage.persist()`;
- предупреждать пользователя, если свободного места недостаточно для новой записи;
- корректно обрабатывать ошибку превышения квоты.

Persistent storage снижает вероятность автоматического удаления данных браузером, но не защищает от ручной очистки данных сайта пользователем, приватного режима или потери устройства.

## Перезагрузка и восстановление

Перезагрузка страницы останавливает активный микрофон и текущий экземпляр `MediaRecorder`. Уже сохранённые в IndexedDB чанки должны сохраниться.

После открытия сайта клиент ищет записи со статусами `recording`, `ready`, `uploading` или `failed` и предлагает:

- продолжить запись;
- завершить и отправить сохранённую часть;
- повторить загрузку;
- удалить запись.

Продолжение выполняется в рамках прежних `session_id` и `recording_id`, но создаёт новый `segment_no`. Новый медиапоток нельзя надёжно дописывать байт-в-байт к старому `WebM`: после перезагрузки `MediaRecorder` создаёт новый контейнер.

Пример:

```text
recording-123
├── segment-1.webm  # до перезагрузки
├── segment-2.webm  # после перезагрузки
└── segment-3.webm
```

Каждый сегмент отправляется отдельным идемпотентным запросом `POST /api/recordings`. Сервер сохраняет сегменты одной логической записи рядом. Их последующая обработка или объединение относится к серверному конвейеру; простая конкатенация байтов разных сегментов не допускается.

Чанк должен сохраняться примерно раз в секунду. При аварийном закрытии страницы это ограничивает потенциальную потерю последним ещё не сохранённым интервалом. Обработчики закрытия страницы не считаются надёжным механизмом сохранения.

## HTTP-загрузка

После остановки клиент переводит запись в `ready`, затем в `uploading` и отправляет её по HTTPS.

Тело `POST /api/recordings` содержит бинарные данные одного медиасегмента. Метаданные передаются заголовками:

```text
X-Session-Id
X-Recording-Id
X-Segment-No
X-Recording-Complete
Content-Type
```

Запрос должен содержать как минимум:

```text
session_id
recording_id
segment_no
mime_type
started_at
stopped_at
audio data
```

`recording_id` используется как ключ идемпотентности: повторная отправка после сетевой ошибки или перезагрузки не должна создавать новую запись на сервере.

Клиент не удаляет локальные чанки при начале загрузки. Они удаляются только после успешного ответа сервера, подтверждающего приём всей записи. Неуспешная или прерванная загрузка остаётся доступной для повторной отправки.

Для ожидаемого размера 5–15 MB достаточно обычного HTTP-запроса с повтором целиком. Resumable/multipart upload можно добавить позднее, если реальные размеры или качество мобильной сети этого потребуют.

## Очистка локальных данных

У IndexedDB и OPFS нет встроенного TTL. Очистка реализуется клиентом.

Очистка запускается:

- сразу после подтверждённой сервером загрузки конкретной записи;
- при начале новой записи;
- периодически, пока сайт открыт.

Рекомендуемые сроки:

- `uploaded` — удалить сразу после подтверждения сервера;
- `ready`, `uploading`, `failed` — хранить 3–7 дней;
- незавершённые `recording` — хранить 1–3 дня.

Периодическая очистка работает только пока сайт открыт. Поэтому проверка при начале новой записи обязательна. При очистке сначала удаляются все чанки и сегменты записи, затем её метаданные.

## Ограничения браузера

- Для доступа к микрофону и OPFS требуется HTTPS, кроме локальной разработки.
- Перезагрузка страницы останавливает запись, но не должна уничтожать уже сохранённую часть.
- Блокировка экрана, сворачивание браузера и энергосбережение на мобильном устройстве могут остановить запись.
- Для MVP пользователь должен держать приложение открытым и не блокировать экран во время записи.
- Захватывается микрофон, а не произвольный системный звук или телефонный звонок.

## Критерии готовности

- Каждая запись связана с сессией.
- Каждый полученный Blob сохраняется в IndexedDB без ожидания окончания записи.
- После перезагрузки незавершённая запись обнаруживается и восстанавливается как логическая запись с новым сегментом.
- Повторная HTTP-загрузка идемпотентна.
- Локальное аудио удаляется только после подтверждения сервера.
- Очистка выполняется при начале новой записи и периодически, пока сайт открыт.
- Ошибки квоты и загрузки видимы пользователю и не приводят к молчаливой потере записи.
